# Wireframes v0 (low-fi)

> สถานะ: ร่างแรก ก่อนมีผล OCR จากสลิปจริง — หน้า "ตรวจและแก้" จะถูกปรับตามจุดที่ OCR ผิดจริงหลัง Phase 1
> mockup ถูกวาดใน session ออกแบบ; เอกสารนี้เก็บ **การตัดสินใจและเหตุผล** ซึ่งสำคัญกว่าหน้าตา

## หลักการออกแบบ

**1. คำถามหลักของแอปคือ "OCR ผิดแล้วผู้ใช้แก้ได้เร็วแค่ไหน" ไม่ใช่ dashboard สวยแค่ไหน**
ถ้าผู้ใช้ต้องเปิดตรวจทุกใบ ก็ไม่ต่างจากพิมพ์เอง แอปจะไม่มีเหตุผลให้ใช้
ดังนั้นทุกหน้าถูกออกแบบให้ **ผู้ใช้ดูแค่สิ่งที่ระบบไม่มั่นใจ** ที่เหลือยืนยันทีเดียว

**2. Mobile-first**
สลิปอยู่ในแกลเลอรีมือถือ (PWA ตอนนี้, Expo ในอนาคต) เดสก์ท็อปเป็นรอง (ลากไฟล์มาวางได้)

**3. ข้อมูลอ่อนไหว = แสดงน้อยที่สุดเท่าที่จำเป็น**
รูปสลิปแสดงแค่ระหว่างตรวจ หลังยืนยันแล้วไม่เก็บรูป (ตาม privacy plan) จึงไม่มีหน้า "ดูรูปสลิปย้อนหลัง"

## หน้าจอ

### 1. อัปโหลด
- เลือกหลายรูปจากแกลเลอรี / ลากมาวาง
- รายการทีละใบพร้อมสถานะ: **อ่านแล้ว · ต้องตรวจ · ซ้ำ (ข้ามให้อัตโนมัติ) · อ่านไม่ได้ (กรอกเอง)**
- "ไม่ต้องรอ ปิดหน้านี้ได้" — OCR ช้า (EasyOCR ~4 วิ/รูปบน CPU) อัปโหลด 20 ใบ = รอเป็นนาที ห้ามบังคับให้ผู้ใช้นั่งจ้อง
- ปุ่มหลักพาไป "ตรวจ N รายการที่ไม่แน่ใจ" ไม่ใช่ "ดูทั้งหมด"

เหตุผลที่บอกสลิปซ้ำตรงนี้ (ไม่ใช่ error): ผู้ใช้มักเลือกรูปทับกับรอบก่อน ระบบควรจัดการเงียบ ๆ แค่บอกให้รู้

### 2. ตรวจและแก้ (หน้าสำคัญที่สุด)
**มุมมองรายการใหม่:** แบ่งเป็น 2 กลุ่ม
- *มั่นใจทุกช่อง* → ติ๊กไว้ให้แล้ว กด "ยืนยัน N รายการ" ทีเดียว
- *ต้องตรวจทีละใบ* → บอกเลยว่า field ไหนที่ไม่แน่ใจ

**มุมมองทีละใบ:**
- รูปสลิป **ซูมไปที่จุดที่ไม่แน่ใจให้อัตโนมัติ** (ต้องมี bounding box ของ field) — ผู้ใช้ไม่ต้องหาเอง
- field ที่ไม่มั่นใจถูกเน้นสี + ขึ้นก่อน; field ที่มั่นใจแสดงเป็นแถวเรียบ ๆ แก้ได้แต่ไม่เรียกร้องความสนใจ
- เลขอ้างอิงแสดงไอคอน QR ถ้าอ่านจาก QR (เชื่อถือได้กว่า OCR — ทดสอบแล้ว OCR อ่าน `ABC` เป็น `48c`)
- หมวดเป็น chip ให้แตะ (เดาไว้ล่วงหน้า) — **ทุกครั้งที่ผู้ใช้เปลี่ยนหมวด = label สำหรับเทรน classifier รายบุคคล (Phase 5)**
- "ยืนยัน แล้วไปใบถัดไป" — flow แบบคิว ไม่ต้องกลับไปหน้ารายการ

### 3. Dashboard
- ยอดเดือนนี้ + แถบงบ + เส้นประ "คาดสิ้นเดือน" + แจ้งเตือนหมวดที่ใกล้เกินงบ
- กราฟรายวัน: เน้นวันที่ผิดปกติ (anomaly)
- ตามหมวด: แถบแนวนอนเรียงมาก → น้อย (อ่านง่ายกว่า pie บนจอมือถือ และเทียบขนาดได้แม่นกว่า)
- จ่ายบ่อยสุด + ป้าย "ทุกเดือน" สำหรับรายจ่ายประจำ (recurring)

**MVP vs ภายหลัง:** ยอดเดือน, งบ, รายวัน, ตามหมวด, จ่ายบ่อยสุด = Phase 3
คาดสิ้นเดือน, วันผิดปกติ, ป้าย "ทุกเดือน" = Phase 5 (ต้องมีข้อมูลสะสมก่อน) — ใน MVP ซ่อนไว้

## สิ่งที่ UI นี้บังคับให้ backend/parser ต้องมี
wireframe มีประโยชน์ตรงนี้: มันเปิดเผย requirement ที่ยังไม่มีในโค้ด

| UI ต้องการ | ตอนนี้มีไหม | ต้องทำ |
|---|---|---|
| ความมั่นใจราย field (เน้น field ที่ไม่แน่ใจ) | ไม่มี — `SlipFields` มีแค่ค่า | parser คืน confidence ต่อ field (จาก OCR confidence + ผ่าน/ไม่ผ่าน regex + เช็คความสมเหตุสมผล) |
| ตำแหน่ง field บนรูป (ซูมอัตโนมัติ) | `OCRResult` เก็บแค่ข้อความ | เก็บ bounding box ต่อบรรทัด (Paddle/EasyOCR มีให้; Typhoon/GCV ต้องดูอีกที) |
| ประมวลผลเบื้องหลัง ปิดหน้าได้ | ไม่มี API | API แบบ job queue: อัปโหลด → job id → poll/stream สถานะ |
| สลิปซ้ำ | ไม่มี | unique key จาก ref (QR ก่อน, OCR สำรอง) + fallback (ยอด, เวลา, ผู้รับ) |
| ธนาคารต้นทาง → ปลายทาง | `bank` มีแค่ฝั่งผู้โอน | เพิ่ม `receiver_bank` (ต้องเพิ่มใน label ด้วย ถ้าจะวัด) |

**confidence เป็นเรื่องสำคัญที่สุดในตารางนี้** — ถ้าไม่มี ระบบแยก "มั่นใจ" กับ "ต้องตรวจ" ไม่ได้ ทั้ง flow ข้างบนพัง
และต้องวัดผล: confidence ที่ดีคือ "ที่บอกว่ามั่นใจ ถูกจริง ≥ 99%" (ไม่งั้นผู้ใช้ยืนยันรายการผิดไปทั้งชุด)
→ เพิ่มเป็น metric ใน Phase 1/2: precision ของกลุ่ม "มั่นใจ" และสัดส่วนสลิปที่ตกกลุ่ม "ต้องตรวจ"

## คำถามที่รอผล OCR จากสลิปจริง
1. field ไหนผิดบ่อยสุด? → ถ้าเป็นเลขอ้างอิง ให้ QR เป็นทางหลัก
2. กี่ % ของสลิปที่ "มั่นใจทุกช่อง"? → ถ้าน้อยกว่า ~60% มุมมอง "ยืนยันทีเดียว" แทบไม่ได้ใช้ ต้องคิดใหม่
3. OCR ช้าแค่ไหนบน server จริง? → ตัดสินว่าต้องมี job queue ตั้งแต่ MVP หรือรอผลแบบ sync ได้
